# Pace Analysis

Анализ темпа в картинговых гонках по письмам с результатами от **Apex Timing**.

Тайминговая система клуба присылает каждому пилоту письмо с итогами сессии: классификация,
времена всех кругов всех участников, личные сектора получателя, история его последних сессий
и усечённые рейтинги (лучшее за неделю, рекорды трассы). Всё это — HTML-вёрстка рассылки,
которую невозможно читать глазами и нельзя сравнивать между гонками.

Проект превращает такие письма в нормальные данные и отвечает на вопросы, которые
письмо не отвечает:

* насколько стабилен пилот, а не только каков его лучший круг;
* кто реально быстрее по темпу, а не по одному удачному кругу;
* есть ли деградация темпа к концу гонки;
* какие круги вообще нельзя считать показателем темпа (трафик, инцидент, аномалия)
  — и это решает человек, а не «умный» фильтр.

Главная находка на эталонных данных: **официальный «Best lap» из письма — это круг джокера
(обязательная срезка) у пяти пилотов из шести**, поэтому как метрика темпа он врёт, и порядок
пилотов по нему отличается от порядка по чистому лучшему кругу. Система находит джокер и пит-стоп
автоматически и всегда показывает обе величины рядом — см.
[«Джокер и пит-стоп»](#джокер-и-пит-стоп).

Полная спецификация формата письма и жёсткий контракт модулей — в [`SPEC.md`](SPEC.md).
Эталонные данные, выверенные вручную по одному письму, — в
[`tests/fixtures/final_a_expected.json`](tests/fixtures/final_a_expected.json).

## Архитектура

Поток данных линейный и односторонний:

```
.eml  ──►  karting.parsing  ──►  ParsedEmail  ──►  karting.storage  ──►  SQLite
                                                        │
                                                        ▼
                                     karting.stats (чистые функции, numpy/scipy)
                                                        │
                                                        ▼
                                     karting.api (FastAPI, JSON)  ──►  web/ (Vite + React)
```

Ключевое правило: **импорт ничего не удаляет и ничего не «исправляет»**. Парсер складывает
в базу то, что было в письме; всё, что похоже на суждение (какой круг считать грязным,
кого с кем сравнивать), живёт в слое статистики и в ручной разметке — и считается на лету.

Каталоги:

```
pace-analysis/
├── PRIMO KARTING _ PRIMO GARA - Final A (FA).eml   # эталонное письмо (имя содержит U+200B!)
├── SPEC.md                     # спецификация формата и контракт модулей (§8)
├── README.md                   # этот файл
├── Makefile                    # install / test / serve / web / import / clean
├── pyproject.toml              # пакет karting, зависимости, pytest, ruff
├── data/
│   ├── pace.db                 # SQLite (не в git)
│   └── raw_emails/             # копии импортированных .eml для провенанса (не в git)
├── karting/
│   ├── models.py               # доменная модель: Club, Session, Driver, Lap, ParsedEmail, ...
│   ├── parsing/                # разбор письма
│   │   └── timeparse.py        # parse_duration / format_duration / parse_gap
│   ├── storage/                # sqlite3 без ORM
│   │   └── schema.sql          # схема, применяется идемпотентно
│   ├── stats/                  # LapFilter, pace_stats, compare_drivers
│   │   └── events.py           # детектор джокера и пит-стопа (SPEC §10)
│   ├── api/
│   │   └── app.py              # FastAPI-приложение
│   └── cli.py                  # import / sessions / show / events / export / serve
├── tests/
│   └── fixtures/
│       └── final_a_expected.json   # ground truth, транскрибированный руками
└── web/                        # Vite + React + TypeScript + Recharts
```

Все длительности везде — **целые миллисекунды** (`int`), поля с суффиксом `_ms`.
Ни в базе, ни в API нет float-времён; `None` означает «времени нет» и никогда не
превращается молча в 0.

## Быстрый старт

Единственное окружение — `/opt/workspace/pace-analysis/.venv`, все Python-команды идут через него
(в `Makefile` это уже зашито).

```bash
make install          # pip install -e ".[dev]" в .venv + npm install для web/
make test             # .venv/bin/python -m pytest -q
```

### 1. Импорт письма

Имя эталонного файла содержит семь невидимых символов U+200B (zero-width space) — **не набирайте
его руками**, пользуйтесь глобом:

```bash
make import                                  # импортирует все *.eml из корня репозитория
make import EML='inbox/*.eml'                # или свой набор писем

# то же самое напрямую:
.venv/bin/python -m karting.cli import *.eml
```

Импорт идемпотентен: повторный запуск того же письма не создаст дублей, а второе письмо той же
гонки (присланное другому пилоту) только дополнит данные — например, добавит его сектора.

Посмотреть, что получилось:

```bash
.venv/bin/python -m karting.cli sessions
.venv/bin/python -m karting.cli show 1
.venv/bin/python -m karting.cli show 1 --sort best               # по чистому лучшему кругу
.venv/bin/python -m karting.cli events 1                         # круги джокера и пита
.venv/bin/python -m karting.cli export 1 --json > final_a.json   # JSON в stdout
.venv/bin/python -m karting.cli export 1 --json final_a.json     # то же самое в файл
```

В отчёте импорта видно, сколько кругов разметил детектор джокера и пит-стопа
(`Tagged 5 joker and 6 pit lap(s).`) и для кого события не нашлись. `show` печатает рядом две
колонки — `BEST` (чистый лучший круг) и `OFFICIAL` (лучший круг из письма, с пометкой `J`, если
это джокер) — и дельту между ними, а колонки `#OFF` / `#PACE` дают два порядка пилотов сразу:
WLAD111 пятый по официальному кругу и второй по чистому. `--sort {position,best,median}`
переставляет таблицу темпа (по умолчанию — порядок финиша).

`export` печатает JSON в stdout; голый флаг `--json` это подтверждает, `--json PATH` пишет
в файл. Письмо без узнаваемой шапки сессии (ни названия, ни времени старта) импорт **отклоняет**
(`[failed]`, код возврата 1) — иначе все такие письма слились бы в одну безымянную сессию.

### 3. Фронтенд

```bash
npm --prefix web install                     # один раз
make web                                     # npm --prefix web run dev
npm --prefix web run build                   # tsc -b && vite build, артефакты в web/dist
```

Дев-сервер Vite поднимается на `http://localhost:5173` и проксирует `/api` на `127.0.0.1:8000`,
так что бэкенд (`make serve`) должен быть запущен параллельно. Если бэкенд поднят на другом
порту (`make serve PORT=9000`), укажите цель прокси через переменную окружения:
`VITE_API_TARGET=http://127.0.0.1:9000 make web`. CORS для дев-фронта в API тоже
включён — фронт можно держать и на другом хосте. Vite слушает `localhost` (IPv6 `::1`), так что
`curl 127.0.0.1:5173` может не ответить — ходите по имени `localhost`.

Если API недоступен, страница переключается на встроенные демо-данные и показывает баннер
«Demo data» с кнопкой «Retry live data». В этом режиме теги не сохраняются: кнопки
Confirm / Remove / Tag as joker выключены, потому что решение человека по SPEC §10.3 главнее
детектора и не должно приниматься «в никуда». Отменённый запрос (смена сессии или фильтра на
лету, StrictMode в дев-режиме) offline-режим не включает.

Точка входа — `web/src/main.tsx` → `web/src/App.tsx`: страница сессии со списком сессий,
классификацией, блоком «официальный vs чистый лучший круг», графиком времён кругов (джокер —
ромб, пит — квадрат; оба вне линии темпа и вне масштаба оси), распределениями (box + strip),
таблицей метрик темпа, панелью разбора джокеров и питов с подтверждением/снятием тегов,
блоком сравнения двух пилотов, рейтингами с пометкой «official, joker-inflated» и загрузкой
`.eml` перетаскиванием.

Если API недоступен, страница переключается на встроенные демо-данные (`web/src/mock/`) и
говорит об этом баннером — вёрстку можно смотреть без бэкенда. Демо-данные генерируются из
выверенного фикстура командой `npm --prefix web run build:mock`; генератор повторяет детектор
из `karting/stats/events.py` один в один и падает, если найденные круги разойдутся с эталонной
гонкой, так что офлайн-режим показывает те же числа, что и живое API.

## Как устроен парсер

### Почему разбор идёт по шапкам таблиц

Письмо — это одночастный `text/html` в `quoted-printable`, свёрстанный вложенными таблицами:
в эталонном письме их **27**, и почти все — чисто оформительские (отступы, рамки, логотип).
Данные лежат в «листовых» таблицах — тех, внутри которых нет других `<table>`.

Соблазн разобрать письмо по индексам («классификация — это таблица №5») выглядит рабочим ровно
до второго письма. Индекс поедет от чего угодно: другой набор секций (в квалификации нет подиума),
другой язык шаблона, отсутствие блока «Track records», лишняя вставка от почтового клиента.
Поэтому единственный признак типа таблицы — **сигнатура её шапки**:

| Шапка | Что это |
|---|---|
| `Rnk · Kart · Driver · Laps · Gap · Best lap` | классификация сессии |
| `Kart · Driver · 1 · 2 · … · N` | lap chart (времена всех кругов) |
| `Lap · S1 · S2 · … · Time` | личные круги получателя с секторами |
| `Rnk · Date · Best lap · Laps` | «Your last sessions» — история получателя |
| `# · Driver · Best lap` | рейтинг: недельный или рекорды трассы (различаются по тексту заголовка над таблицей) |

Заголовки распознаются по словарю синонимов EN/FR/RU (`Rnk|Clt|Поз`, `Driver|Pilote|Пилот`,
`Best lap|Meilleur tour|Лучший круг`, …). Перед сравнением текст нормализуется: casefold,
схлопывание пробелов, `&nbsp;` (U+00A0) и zero-width space (U+200B) → обычный пробел.
Эти невидимые символы есть даже в `Subject`, так что нормализация — не паранойя.

Таблица, которую не удалось классифицировать, не пропадает: она уходит в
`ParsedEmail.unparsed` вместе с сигнатурой шапки и строками. Ничего не терять и ничего
не выдумывать — главное требование к парсеру.

### Особенности, которые обязательно ломают наивную реализацию

* **Lap chart свёрнут по 10 кругов в строку.** Один пилот = несколько подряд идущих `<tr>`:
  в первом заполнены `Kart` и `Driver`, в следующих эти ячейки пустые. Ширина обёртки берётся
  из числа колонок-номеров в шапке, а не хардкодится: `1..N` в шапке — это и есть N.
  Признак нового пилота — непустая ячейка `Driver`, а не пустая строка-разделитель.
* **Номер круга — это позиция ячейки**, а не порядковый номер непустого значения.
  Круг 1 в эталоне показан как `-` (старт с решётки, время не засчитано): время `None`,
  но круг существует и нумерация не съезжает.
* **Признак «лучший круг» — это цвет.** Ячейка лучшего круга пилота имеет
  `background-color:#515151` и `color:#FFFFFF`. Это единственный источник флага `is_best`
  на уровне круга, поэтому он сверяется с колонкой `Best lap` классификации (в эталоне сходится
  у всех шести пилотов); расхождение — предупреждение, а не тихое исправление.
* **Заголовок сессии парсится с конца.** Строка
  `PRIMO GARA - Final A (FA) - 03.08.2026 à 21:40 (Karting track)` содержит ` - ` внутри
  названия, поэтому split по первому дефису даёт мусор. Регулярка с конца выделяет дату, время,
  трассу; скобочный суффикс названия становится `session_code = "FA"`, остаток —
  `session_name = "PRIMO GARA - Final A"`. Разделитель даты и времени зависит от языка шаблона:
  `à` / `at` / `в` / `um`.
* **Время сессии — локальное время площадки** и хранится наивным `datetime`.
  Заголовок `Date:` письма — это время сервера Apex (в эталоне `+02:00` при московской площадке),
  и конвертировать по нему нельзя.
* **Идентификаторы берутся из ссылки отписки**:
  `?center=51&unsubscribe&client=10001&id=…&key=…` → `club.external_id = "51"`,
  `driver.external_id = "10001"` для получателя (ник может поменяться, id — нет).
* **Кириллические ники** (`ИГОРЬ53`) не транслитерируются и не «чинятся».

### Валидация

Парсер не падает на странных данных — он их проговаривает. `ParsedEmail.warnings` наполняется,
когда:

* число кругов в lap chart не совпадает с колонкой `Laps` классификации;
* `Best lap` из классификации не равен минимуму по кругам пилота;
* подсветка `#515151` стоит не на минимальном круге;
* `sum(sectors) != time_ms` (допуск 0 мс — Apex не округляет);
* времена получателя в lap chart расходятся с его личной таблицей секторов;
* пилот с подиума отсутствует в классификации.

Режим `parse_email_file(path, strict=True)` превращает любые warnings в `ParseError` —
удобно для тестов и для пакетного импорта архива.

### Формат времени

`karting.parsing.timeparse` понимает `28.872`, `1:02.345`, `1'02.345`, `1:02,345`, `01:02.345`,
`1:02:03.456`, а `-`, `--`, пустую строку и `&nbsp;` отдаёт как `None`. Дробная часть
нормализуется по длине (`28.8` → 28800 мс, а не 28.8 × 1000). Обратно: `28.872` для
времён меньше минуты, `1:02.345` — для больших. Гэп разбирается в пару
`(gap_ms, gap_laps)`: `2.022` → `(2022, None)`, `2 Laps` → `(None, 2)`.

## Хранилище

SQLite (`data/pace.db`), `sqlite3` из stdlib, без ORM, `PRAGMA foreign_keys=ON`,
`journal_mode=WAL`. Схема (`karting/storage/schema.sql`) применяется идемпотентно при открытии.

* **Ключ сессии — `(club_id, name, code, started_at)`, а не message-id.** Одну и ту же гонку
  присылают несколько писем — разным получателям. Дедупликация по письму — отдельно, в таблице
  провенанса `email_import` (`message_id` UNIQUE + sha256 файла + sha256 самого разбора,
  чтобы вход без заголовков — `parse_html` — тоже дедуплицировался). Если сессию удалили,
  а письмо осталось в архиве, повторный импорт того же письма пересоздаёт её, а не падает.
* **Пилот опознаётся по `external_id`, а не по нику** (SPEC §1.8). Пришло письмо, где тот же
  Apex-`client` подписан новым ником, — это переименование: строка пилота одна, ник обновляется,
  факт переименования пишется в `import_conflict`. Ник как ключ используется, только когда
  `external_id` в письме нет.
* **Слияние, а не перезапись.** Второе письмо той же гонки добавляет только новое (свои сектора),
  расхождения по совпадающим ключам не затирают данные, а попадают в `ImportReport.conflicts`.
  Это касается и флага `is_best`: у пилота в сессии ровно один лучший круг, и если второе письмо
  подсвечивает другой — побеждает сохранённый, а разногласие уходит в конфликты. Повтор одного
  и того же ключа **внутри одного письма** (сдвоенная таблица кругов) тоже сливается и
  отмечается конфликтом, а не отвергает письмо целиком.
* **Сырое письмо сохраняется** (`data/raw_emails/`), чтобы любой вывод можно было проследить
  до исходника. У базы `":memory:"` каталога сырых писем нет вовсе — тестовый прогон не оставляет
  файлов в рабочем каталоге (нужны копии — передайте `open_db(":memory:", raw_dir=...)`).
* **Круги неизменяемы.** Импорт никогда не правит `lap` задним числом; человеческие суждения
  живут в отдельной таблице `lap_annotation` (см.
  [«Ручная разметка кругов»](#ручная-разметка-кругов)).
* **Джокер и пит размечаются в той же транзакции, что и импорт**, поэтому сессия никогда не
  бывает видна без своих не-темповых кругов. Строки детектора помечены `source='auto'` и
  переписываются целиком при каждом пересчёте; ручные строки не трогаются никогда.

Каждый импорт возвращает `ImportReport`: `session_id`, `session_created`, `already_imported`,
`inserted_laps`, `updated_laps`, `inserted_entries`, `conflicts`, `warnings`, а также
`auto_jokers`, `auto_pits`, `drivers_without_joker`, `drivers_without_pit`.

Работа из кода:

```python
from karting.storage import open_db

with open_db("data/pace.db") as db:
    for row in db.list_sessions():
        print(row["id"], row["name"], row["started_at"])
```

Для тестов путь `":memory:"` поддерживается. Соединение открывается с
`check_same_thread=False`, а все записи сериализуются внутри объекта `Database`: ASGI-зависимость
и обработчик запроса живут в разных потоках пула, и это нормально.

## Что умеет статистика

Модуль `karting.stats` — чистые функции на numpy/scipy, никакого доступа к БД. Вход —
последовательность `LapPoint(lap_number, time_ms, sectors, tags)`, поведение фильтра целиком
задаётся `LapFilter`; ни одно правило не «зашито».

**Метрики темпа** (`pace_stats`): число кругов и число зачтённых, `best`, `median`, `mean`,
усечённое среднее (10 %), `std`, `IQR`, `MAD`, `cv = std/mean`, `consistency = std/median`,
теоретический лучший круг (сумма лучших секторов, если сектора есть) и деградация — наклон
OLS «время круга ~ номер круга» в мс/круг с p-value. Вместе с числами возвращается список
`excluded: list[LapFlags]` — по каждому выброшенному кругу видно, почему он выброшен
(`missing`, `first_lap`, `tag:penalty`, `slow_outlier`, `fast_outlier`).

**Детекция выбросов** робастная, на медиане и MAD: круг «грязный», если
`time > median + k · 1.4826 · MAD` (по умолчанию `k = 3`) или времени нет. Первый круг
по умолчанию отбрасывается — это старт/выезд, а не темп.

Если MAD вырождается в ноль (половина кругов совпала до миллисекунды), масштаб берётся из
IQR (`IQR / 1.349`), а если и он нулевой — из среднего абсолютного отклонения (`1.2533 · MeanAD`).
Ноль остаётся только тогда, когда все круги идентичны: тогда выбросов действительно нет.
Круг без времени в числовую выборку попасть не может ни при каких настройках — `drop_missing`
управляет лишь тем, показывать ли его в `excluded` как отброшенный круг.

Усечённое среднее честно усекает: не меньше одного круга с каждого края начиная с пяти кругов,
а на выборке меньше пяти возвращается `None` — «10 % усечения», которое ничего не усекло,
это просто среднее под другим именем.

Важная асимметрия: **быстрые аномалии по умолчанию не выбрасываются**. Круг с
`time < median − k · MAD` получает отдельный флаг `suspicious_fast` и остаётся в выборке.
Медленный круг почти всегда объясним (трафик, разворот, штраф), а необъяснимо быстрый круг —
это либо реальный потолок пилота, либо артефакт, и автоматика не имеет права решать это за
человека. Отсюда `LapFilter(drop_fast_outliers=False)` в дефолте и ручная разметка ниже.
Со времён SPEC §10 у самой частой быстрой аномалии есть имя: это круг джокера, и он отсекается
осмысленным тегом, а не слепым статистическим порогом. Дефолтный
`LapFilter.exclude_tags = {joker, pit, penalty, boost, invalid, outlier}`.

**Сравнение двух пилотов** (`compare_drivers`): разности средних и медиан, Welch t-test,
Mann–Whitney U, Levene/Brown–Forsythe на равенство дисперсий, bootstrap-CI разности медиан
(10 000 ресэмплов, фиксированный seed), размеры эффекта Cliff's delta и Hedges' g.

> **Честная оговорка (она же в `DriverComparison.caveats`).** Все эти тесты предполагают
> независимые наблюдения, а круги одной гонки независимыми не являются: пилоты едут в одном
> трафике, по одной и той же деградирующей резине и трассе, топливо вырабатывается, лидер едет
> в чистом воздухе, а замыкающий — нет. Плюс выборка крошечная: 19–20 кругов на пилота, и после
> фильтрации остаётся меньше. Поэтому p-value здесь — **описательная величина, а не вывод**:
> «пилот A статистически значимо быстрее пилота B» из одной гонки не следует. Разность медиан
> с bootstrap-CI и размер эффекта информативнее p-value; правильный ответ на вопрос «кто быстрее»
> набирается из многих сессий, чего система пока не умеет (см. roadmap).

## Джокер и пит-стоп

**Доменное правило, подтверждённое владельцем данных 11.08.2026 (SPEC §10).** В этом формате
каждый пилот обязан ровно один раз проехать **джокер** (срезка — круг становится примерно
на 1.9 с быстрее) и ровно один раз **заехать на пит-стоп** (примерно на 13 с медленнее).
Ни один из этих кругов не является темпом, поэтому оба по умолчанию исключаются из анализа.

В эталонном письме (`PRIMO GARA - Final A`, 6 пилотов, по 20 кругов, первый круг без времени)
это видно невооружённым глазом:

| Пилот | База (медиана) | Пит-стоп | Джокер (он же официальный best) |
|---|---|---|---|
| KOLYA11 | 27.971 | №17 — 41.889 | №19 — 26.012 |
| WLAD111 | 28.058 | №19 — 40.342 | №3 — 26.788 |
| TWG | 27.986 | №3 — 44.455 | №14 — 25.845 |
| DENISENKO | 28.396 | №5 — 40.876 | №15 — 26.341 |
| PHREEMAN | 28.400 | №18 — 40.993 | №5 — 26.359 |
| ИГОРЬ53 | 28.723 | №14 — 42.164 | не детектируется |

У ИГОРЬ53 джокер не находится, и это **корректное поведение, а не баг**: джокер можно проехать
с потерей времени, и тогда он статистически неотличим от обычного круга (его круг 15 = 32.178
идёт сразу после пита на круге 14). Отсутствие джокера — мягкий сигнал. Отсутствие **пит-стопа** —
жёсткий: пит обязателен для каждого, поэтому такой случай попадает в предупреждения и
сопровождается предложенным кругом (самым медленным), чтобы человек подтвердил его одним
действием.

### Почему не MAD, а отношение к собственной базе

Порог «медиана ± 3·MAD» находит джокер безошибочно, но для пита даёт ложные срабатывания:
у стабильного пилота MAD мал, и обычный подпорченный круг (29.558 и 28.276 у KOLYA11, 29.349
и 29.536 у PHREEMAN) вылетает за порог. Отношение к **собственной робастной базе** разделяет
классы с огромным запасом:

| | худший НЕ-пит круг | лучший пит-круг | лучший НЕ-джокер круг | худший джокер |
|---|---|---|---|---|
| отношение к базе | 1.120 | 1.438 | 0.987 | 0.954 |

Отсюда дефолты `pit_ratio = 1.25` и `joker_ratio = 0.97` — оба сидят посреди широкой пустой
полосы. База считается в два прохода: сначала грубая медиана кругов без первого, затем медиана
по кругам, которые первый проход не счёл кандидатами, — чтобы событие не тянуло за собой ту
величину, с которой его же и сравнивают.

Метод держится на том, что аномалии — меньшинство кругов пилота. Когда это не так (пилот
заехал на пит, попал в аварию и сошёл через четыре круга), медиана садится на аномалии, а
обычные круги пересекают порог джокера. Детектор такие случаи **не** превращает в события, а
отказывается и пишет предупреждение — иначе тег `joker` выбросил бы из статистики как раз
лучший чистый круг пилота. Два признака испорченной базы: кандидатов одного вида не меньше
половины кругов, либо «джокер» быстрее базы более чем на 15% (сокращение стоит ~1.9 с из
~28 с, то есть ~0.93; самый слабый джокер эталонной гонки — 0.954). Круги с неположительным
временем отбрасываются с предупреждением, а не читаются как рекордно быстрые.

### Аномалия заперта в одном секторе

Личная таблица секторов есть только у получателя письма, и она подтверждает, что оба отклонения
односекторные:

| Круг WLAD111 | S1 | S2 | Время |
|---|---|---|---|
| типичный | 13.9–14.2 | ≈14.0 (13.83–14.72) | ≈28.0 |
| №3 — джокер | **12.241** | 14.547 | 26.788 |
| №19 — пит | 13.999 | **26.343** | 40.342 |

Джокер набран целиком в первом секторе (−1.776 с к медиане сектора), пит — целиком во втором
(+12.327 с). Проверка секторов **не отменяет** событие (13 секунд остаются 13 секундами), а
уточняет `sector_index` и двигает `confidence`: подтверждение +0.08, опровержение −0.25.
У пилотов без секторов проверка просто недоступна, и это не считается уликой против события.

## Официальный лучший круг против чистого

Прямое следствие правила про джокер: **колонка «Best lap» из письма — это круг джокера у пяти
пилотов из шести**, то есть как метрика темпа она врёт. Поэтому и дашборд, и CLI, и `/stats`
всегда показывают рядом две величины и дельту между ними:

| Пилот | Официальный best | Чистый best | Δ | Место по официальному | Место по чистому |
|---|---|---|---|---|---|
| TWG | 25.845 (джокер) | 27.791 | +1.946 | 1 | 1 |
| WLAD111 | 26.788 (джокер) | 27.804 | +1.016 | 5 | **2** |
| KOLYA11 | 26.012 (джокер) | 27.897 | +1.885 | 2 | 3 |
| DENISENKO | 26.341 (джокер) | 28.232 | +1.891 | 3 | 4 |
| PHREEMAN | 26.359 (джокер) | 28.249 | +1.890 | 4 | 5 |
| ИГОРЬ53 | 28.380 | 28.380 | +0.000 | 6 | 6 |

WLAD111 по официальному кругу пятый, по чистому — второй, в 13 мс от лидера. Это не декоративная
деталь, а основная ценность продукта.

Каждая строка `/api/sessions/{id}/stats` несёт `official_best_ms`, `official_best_source`,
`official_best_lap_number`, `official_best_lap_id`, `official_best_tags`, `official_best_is_joker`
и `best_delta_ms = best_ms - official_best_ms`; на уровне ответа есть сводка `official_best`.
В `karting.cli show` это колонки `BEST` / `OFFICIAL` (с пометкой `J`) / `Δ` плюс `#OFF` / `#PACE`.
`/api/drivers` и `/api/drivers/{nickname}/history` отдают тот же официальный круг, поэтому и там
он подписан: `official_best_based`, `joker_inflated`, `best_lap_label`.

То же предупреждение относится к таблицам «Best times of the week» и «Track records» из письма:
они построены на официальных лучших кругах и почти наверняка тоже содержат джокеры.
`/api/sessions/{id}/rankings` помечает их флагами `official_best_based`, `joker_inflated` и
подписью `official, joker-inflated`; UI показывает эту подпись рядом с таблицами.

## Ручная разметка кругов

Разметка — это отдельный слой поверх неизменяемых кругов. Таблица `lap_annotation`
(`lap_id`, `tag`, `note`, `created_at`, `source`), `UNIQUE (lap_id, tag, source)`,
справочник тегов:

| Тег | Смысл | Исключается фильтром по умолчанию |
|---|---|---|
| `joker` | обязательная срезка (~1.9 с быстрее), не темп | да |
| `pit` | обязательный заезд на пит-стоп (~13 с медленнее), не темп | да |
| `penalty` | штраф, наложенный на круге | да |
| `boost` | круг с искусственным преимуществом | да |
| `invalid` | круг не должен учитываться вообще | да |
| `outlier` | ручная пометка «аномалия» | да |
| `traffic` | потеря времени в трафике | нет |
| `incident` | контакт, разворот, вылет | нет |
| `clean` | явное подтверждение, что круг чистый | нет |

`traffic` и `incident` по умолчанию **не** выбрасываются: они описывают гонку, а не ошибку
измерения, и решение «считать ли их темпом» зависит от вопроса. Список исключаемых тегов —
параметр (`LapFilter.exclude_tags`, query-параметр `exclude_tags` в API).

### Два источника и приоритет человека

У каждой строки разметки есть `source`:

* `manual` — поставил человек (CLI, API, дашборд);
* `auto` — поставил детектор джокера и пита; строки этого источника **одноразовые**,
  `Database.detect_and_tag_events(session_id, config)` удаляет их для сессии и пишет заново.

**Правило приоритета (SPEC §10.3): если у круга есть хотя бы одна ручная пометка, автоматические
для этого круга игнорируются целиком.** Человек посмотрел на круг — его вердикт главнее
детектора, и «снять» ошибочный авто-тег можно, просто поставив свой (например `clean`).
Ручные строки детектор не читает при записи и не удаляет никогда.

Правило действует и **на уровне отчёта**, а не только на уровне таблицы: ручные пометки
приходят в детектор через `LapPoint.tags`, поэтому круг, помеченный человеком как `joker`
или `pit`, считается подтверждённым событием (`confidence = 1.0`, в базу темпа не входит), и
пилот уходит из `drivers_without_joker` / `drivers_without_pit`, а `complete` в ответе API
становится `true`. Обратное тоже верно: если человек пометил круг иначе (`traffic`), находка
детектора остаётся видимой в `events` с пометкой «overruled», но в зачёт не идёт — пилот
считается без джокера. Авто-копия ручного вердикта в таблицу не пишется.

Как это видно в данных:

* `Database.lap_tags(session_id)` и поле `tags` каждого круга — **действующие** теги
  (правило приоритета уже применено);
* `Database.lap_annotations(session_id)` и поле `annotations` — **сырые** строки обоих
  источников, включая перекрытые;
* круг в `/api/sessions/{id}` дополнительно несёт `manual_tags`, `auto_tags`, `effective_tags`
  и `manually_annotated`, так что клиент отличает «детектор предложил» от «человек решил».

Перезапуск детектора идемпотентен: у неизменившихся строк сохраняются `id` и `created_at`,
поэтому повторный вызов оставляет таблицу побайтово прежней.

Сначала нужен `lap_id` — он приходит в деталях сессии:

```bash
curl -s http://127.0.0.1:8000/api/sessions/1 | .venv/bin/python -m json.tool | head -40
```

Пометить и снять пометку:

```bash
curl -s -X POST http://127.0.0.1:8000/api/laps/57/tags \
     -H 'Content-Type: application/json' \
     -d '{"tag": "traffic", "note": "lapped a slower kart in S2"}'

curl -s -X DELETE http://127.0.0.1:8000/api/laps/57/tags/traffic
```

Из Python (например, чтобы разметить пачку кругов скриптом):

```python
from karting.storage import open_db

with open_db("data/pace.db") as db:
    laps = db.session_laps(1)
    for lap in laps:
        if lap["driver"] == "WLAD111" and lap["lap_number"] == 19:
            db.add_lap_tag(lap["id"], "pit", "S2 26.343 vs usual 14.0 — confirmed pit stop")
```

После разметки метрики достаточно просто запросить заново — они считаются на лету:

```bash
curl -s 'http://127.0.0.1:8000/api/sessions/1/stats?exclude_tags=joker,pit,penalty,boost,invalid,outlier'
```

## HTTP API

Базовый префикс `/api`, все времена — целые мс в полях `*_ms`.

| Метод | Путь | Что возвращает |
|---|---|---|
| GET | `/api/health` | статус и число сессий |
| GET | `/api/sessions` | список сессий |
| GET | `/api/sessions/{id}` | сессия, клуб, классификация, все круги с тегами |
| GET | `/api/sessions/{id}/stats` | метрики темпа по каждому пилоту + официальный vs чистый best |
| GET | `/api/sessions/{id}/events` | круги джокера и пита (только чтение) |
| POST | `/api/sessions/{id}/events/detect` | пересчитать и сохранить авто-теги джокера/пита |
| GET | `/api/sessions/{id}/compare?a=&b=` | сравнение двух пилотов со статтестами |
| GET | `/api/sessions/{id}/rankings` | недельный рейтинг и рекорды трассы (с пометкой «joker-inflated») |
| GET | `/api/drivers` | пилоты (`source`: `session` или `ranking`) |
| GET | `/api/drivers/{nickname}/history` | история пилота |
| POST | `/api/imports` | multipart `files=[]` (.eml) → отчёты об импорте |
| GET | `/api/tags` | справочник тегов |
| POST | `/api/laps/{lap_id}/tags` | поставить тег → 204 |
| DELETE | `/api/laps/{lap_id}/tags/{tag}` | снять тег → 204 |

Общие query-параметры фильтра для `/stats` и `/compare`: `mad_k`, `drop_first_lap`,
`drop_slow_outliers`, `drop_fast_outliers`, `exclude_tags` (csv), `min_laps`.

Каждая строка `/stats` кроме полей `PaceStats` содержит `pace_delta_to_best_ms`,
`suspicious_fast_lap_numbers` (круги, которые фильтр **оставил** в выборке, но пометил как
подозрительно быстрые — в `excluded` их нет по определению, а разметить их должен человек)
и блок `official_best_*` / `best_delta_ms` из раздела
[«Официальный лучший круг против чистого»](#официальный-лучший-круг-против-чистого).

У `/events` и `/events/detect` свои query-параметры: `pit_ratio` (> 1), `joker_ratio` (0…1)
и `one_per_driver`. Перевёрнутый порог — это `422`, а не «молча ничего не нашли». Ответ несёт
`events`, `drivers_without_joker` / `drivers_without_pit` / `drivers_with_multiple`,
`pit_candidates` (предложенный круг для каждого пилота без пита), `warnings`, `counts`,
`complete` и эхо `config`; у каждого события есть `lap_id`, `applied` и `overridden_by_manual`,
то есть состояние хранилища, а не только вердикт детектора.

`POST /api/imports` всегда отвечает `200` и массивом отчётов по каждому файлу — статус смотрите
в `status` (`imported` / `merged` / `already_imported` / `failed`). `400` возвращается только
если ни один файл запроса импортировать не удалось; так один и тот же код клиента работает
и для одного файла, и для пачки. Отчёт несёт ещё и `auto_jokers` / `auto_pits` /
`drivers_without_joker` / `drivers_without_pit`: автотегирование идёт в той же транзакции,
что и сам импорт, поэтому сессия никогда не видна без своих джокеров и питов.

Ошибки — стандартный `{"detail": "..."}`: 404 на неизвестную сессию или пилота,
422 на некорректный запрос (включая id вне диапазона 64-битного целого), 400 на нераспарсенный
`.eml`. Ответы `500` намеренно безлики — `{"detail": "Internal server error…", "error_id": "…"}`;
тип исключения, путь к базе и прочие внутренности пишутся в лог сервера под тем же `error_id`.

Интерактивная документация — `http://127.0.0.1:8000/docs`.

## Разработка

```bash
make test                                    # весь набор тестов
.venv/bin/python -m pytest tests/<файл> -q   # точечно, по одному файлу
.venv/bin/python -m pytest -q -k parsing     # по имени теста
```

Конвенции:

* Python 3.12, единственное окружение — `./.venv`; новых venv не заводим, `pip install`
  только через `.venv/bin/pip` (или `make install`).
* Типизация обязательна на всех публичных функциях; докстринги и комментарии — на английском,
  тексты в CLI и UI — тоже.
* Длина строки 100 (`[tool.ruff]` в `pyproject.toml`).
* Сигнатуры публичных модулей зафиксированы в `SPEC.md` §8: добавлять необязательные аргументы
  с дефолтами можно, менять имена и форму возвращаемых структур — нет.
* `make clean` убирает только кеши и артефакты сборки; `data/` он не трогает —
  базу удаляйте руками, осознанно.

## Дальше (roadmap)

Ничего из перечисленного пока не реализовано — это план, а не описание системы.

* **Автоматический забор почты.** Сейчас письмо кладут в репозиторий или загружают через
  `POST /api/imports` руками. Хочется фонового IMAP/Gmail-коннектора, который сам забирает
  новые письма от Apex Timing, складывает их в `data/raw_emails/` и импортирует —
  идемпотентность по `message_id` для этого уже есть.
* **Множественные сессии как первоклассный объект.** База уже рассчитана на много гонок и на
  слияние писем от разных получателей, но интерфейс сегодня сессионно-центричный: одна страница —
  одна гонка. Нужны списки, фильтры по клубу/трассе/категории и нормальная навигация по архиву.
* **Сравнение по сессиям.** Динамика темпа пилота от гонки к гонке, поправка на трассу и
  категорию, оценка «стал быстрее или день был быстрый» (за счёт общего смещения по всем
  участникам сессии). Именно это чинит главную оговорку из раздела о статистике: много сессий
  дают ту вариативность, которой не хватает внутри одной гонки.
* **Рейтинг пилотов Elo / TrueSkill.** Рейтинг по результатам очных встреч в сессиях — с учётом
  силы соперников, а не суммы призовых мест. TrueSkill интереснее Elo для заездов больше двух
  человек и умеет честно показывать неопределённость для новичков.
